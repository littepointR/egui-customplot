# 阶段 5：Painter 瓶颈与 GPU 投入决策

日期：2026-11-15。**记录当前决策，不代表 GPU 路径或阶段 5 的完整验收。**

## 决策

现阶段继续使用宿主 `egui::Painter`，不增加第二个 device、隐式独立窗口或只支持单像素细线的“GPU 完整后端”。优先补齐二维数据语义、原始拾取与导出。`wgpu` 仍保留为后续可选后端方向，不能由此删除阶段 9 的深度渲染要求。

## 已观察的证据

- [阶段 4 原始 CPU 记录](benchmarks/2026-11-15-stage4-windows-cpu.csv)：相同 1920×1080 / DPI 1 / 单调 X / 无标记条件下，100 万与 1000 万点显式 MinMax 全区，UI 构建 + tessellation p95 分别为 1.1654 / 3.2124 ms。1000 万点 Exact 窄区仍访问 9,999,999 段，Visible 访问 10,001 段。改善首先来自查询，不能归功于 GPU。
- 缓存命中只跳过查询 / 裁剪，仍要复制路径和 tessellate。千百万点的索引拾取仍可能访问密集 X 列；GPU 并不自动解决原始数据定位。
- [阶段 6 热力图记录](benchmarks/2026-11-15-stage6-heatmap-windows-cpu.csv)：1,048,576 cell 全区精确四边形的 UI 构建 / tessellation p95 为 60.7130 / 77.1864 ms，窄区访问 289 cell。表明**全区精确网格几何是明确的 CPU / 容量风险**，不应把折线 LOD 的成本结论套用到热力图。
- 全网格的 geometry capacity 为 109,051,904 B；这不是 GPU 显存，也不是进程总内存。

## 推论与取舍

目前折线切片没有足够证据证明维护宽线 / 接合 / 端帽 / 虚线 / AA 的独立 GPU 后端具有必要收益；暂缓是投入优先级决策，不是“Painter 对所有图足够快”的结论。

大数值网格值得首先研究纹理路径：需明确非均匀边缘、坐标 log、NaN 空洞、色域变化、精确单元拾取与资源回收。不能通过自动平滑、静默 LOD 或修改缺失值来通过性能门槛。

## 重新评估条件与未知项

1. 在固定机器的真实宿主上分别测 UI、tessellation、上传 / 提交、GPU timestamp 和呈现等待；保留无图宿主对照。
2. 4 / 16 图、百万 cell 热力图及高密度散点成为实际瓶颈时，先验证查询、批处理 / 纹理与索引方案，再做同条件 Painter / wgpu 实验。
3. 用参考图像与导航 / 拾取测试验证 log、反向、双轴、透明层序、AA、DPI 和裁剪一致性；后端不兼容应明确报错 / 正常回退，不能静默缺图。
4. 记录 CPU/GPU 缓冲预算、增量上传和释放；收益应覆盖新增依赖、维护及平台成本。

尚无同条件 wgpu 实现、GPU 时间、驱动驻留、端到端帧率和跨平台视觉对照，故阶段 5 的这些门槛仍未完成。
